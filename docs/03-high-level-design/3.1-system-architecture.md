
# 3.1 System Architecture

### 3.1.1 Overall design

[View the CyberFort Nexus component and data flow diagram](../../diagrams/component-data-flow-diagram.png).

The corporate **GW Switch** mirrors all network traffic to a dedicated Ethernet port. The **Capture & Flow Export** component receives this mirrored traffic on a dedicated network interface. It is built on a proven open-source capture engine and runs two processing paths:

**Header Inspection** processes every packet but reads only protocol headers (ADR-001). It keeps a table of active connections and, when a connection ends or times out, emits one compact flow record containing the metadata required by FR-NF-002. Each record is tagged as *inbound* or *outbound* and is published to the corresponding topic (`inbound`, `outbound`) on the durable event log.

**Stream Reassembly** applies only to inbound POP3 and FTP sessions (AS-005). It reconstructs the TCP byte stream, extracts transferred files, complete e-mail messages, and e-mail attachments, writes each object to **Bucket Storage**, and publishes a `file.received` event carrying the object key and light metadata (sender, recipients, source and destination IP). The stored content itself never travels through the event log.

**Network Forensic** consumes both the `inbound` and `outbound` topics and writes every flow record, in batches, to the **Columnar Database**, where netflow metadata is indexed and searchable for the 3-month retention period (FR-NF-003, FR-NF-004).

**Command & Control** consumes the `outbound` topic only (FR-CC-001). The machine-learning model is deployed inside the C&C process and scores flows in batches, so analyzing all outbound traffic does not require one call per flow (ADR-004). Flows with score > 0.70 (FR-CC-003) are written as a separate *detections* dataset to the Columnar Database - flow reference, score, model version, timestamp - retained for 1 year (FR-CC-006), and published as `alert.raised` events. Detections are separate records, not updates to existing flow records, so the write path stays append-only.

**File Analysis** consumes `file.received` events immediately as they arrive (ADR-006). For each event it fetches the stored object from Bucket Storage, obtains a verdict from the **3rd-party Antivirus** over its REST API, and writes a scan report for every scanned file or e-mail to the Columnar Database (FR-FA-004). Scan reports are retained for 1 year (FR-FA-009). Objects not considered a threat are deleted from Bucket Storage; objects with a *malicious* or *suspicious* verdict are retained for the 3-month evidence period (FR-FA-005/007/008) and an `alert.raised` event is published.

The `alert.raised` topic has two independent consumers:

- The **Investigation Portal Backend** persists incoming alerts to the **Relational DB** and makes them visible to analysts within the 60-second budget (NFR-007).
- The **Automatic Cyber Investigator (ACI)** correlates alerts with netflow data queried from the Columnar Database (FR-ACI-003) and creates investigations in the Relational DB. At creation time the ACI copies the correlated evidence into an immutable snapshot stored with the investigation, so an investigation stays complete and reviewable even after netflow retention has deleted the underlying records (ADR-005).

The **Investigation Portal Frontend** communicates only with the Portal Backend. The Backend reads the Columnar Database for manual deep investigation over the full retention window (FR-INVP-004, NFR-006) and reads and writes investigations, alerts, and users in the Relational DB. Manually created investigations follow the same snapshot rule as ACI-created ones.

Persistence follows the shape of the data rather than a single database for everything (ADR-003): append-only, time-range-queried data (flows, detections, scan reports) goes to the Columnar Database; mutable, individually owned entities (alerts, investigations, users) go to the Relational DB; opaque binary objects (extracted files and complete e-mail messages) go to Bucket Storage.

Availability of the capture tier is achieved by fast automatic restart of failed capture instances rather than by duplicating the mirror feed (ADR-007): a restart causes a blind window of seconds, well inside the 5-minute data-loss allowance of NFR-003, at a fraction of the cost of a duplicated feed.

Significant design decisions are recorded as ADRs in `docs/adrs/`.

### 3.1.2 Logical Deployment View

[View the CyberFort Nexus Logical Deployment View](../../diagrams/logical-deployment-view.png).

The diagram presents the logical deployment of CyberFort Nexus within the customer's premises (NFR-021). It groups the solution into the **Capture Tier**, **Platform Compute Tier**, and **Data Tier**, and shows the main external interactions with the corporate network, SOC workstation, and 3rd-party Antivirus.

The **Capture Tier** runs on one or more capture hosts connected to the GW Switch monitoring port through a dedicated network interface. Capture instances run under the container platform with health checks and automatic restart. At Medium and XLarge, the mirrored traffic is split across multiple capture instances so a failure affects only part of the feed (ADR-007).

The **Platform Compute Tier** runs the durable event log and the stateless processing and portal components. Components are packaged as container images (NFR-022) and can be replicated independently according to their workload.

The **Data Tier** hosts the Columnar Database, Relational DB, and Bucket Storage; storage capacity is provisioned for the selected sizing tier and retention periods (NFR-008).

SOC analysts access only the Investigation Portal Frontend from the internal corporate network. File Analysis communicates with the separately deployed 3rd-party Antivirus over its REST API. All inter-component communication is encrypted and mutually authenticated (NFR-017). Exact node counts, resource allocations, and storage layouts are determined during deployment sizing and are intentionally not fixed by this HLD.
